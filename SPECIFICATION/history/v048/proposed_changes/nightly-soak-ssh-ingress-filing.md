## Proposal: Nightly soak files through the on-tailnet SSH write ingress and holds no database credential

### Target specification files

- non-functional-requirements.md

### Summary

Align the ratified nightly chore-filing clause with the on-tailnet CI beads write surface `dolt-server` has now delivered. The clause's dedup SEMANTICS are unchanged and remain correct — dedup against OPEN chores, re-filing after a chore is closed. What changes is the filing MECHANISM (an SSH forced-command ingress instead of CI reaching the work-items backend directly), the way the finding identity is carried (a bounded fingerprint in a metadata field plus an external ref), and the credential posture: CI no longer holds a database credential at all. Adds a fail-closed requirement that the nightly run on the self-hosted, on-tailnet runner pool. It also REMOVES, rather than relocates, the ratified "top of the rank order" placement obligation: the ingress's single `bd create` files at the beads default `open` status, outside the orchestrator's lifecycle states, so no actor performs any transition such an obligation could bind to. The gap that removal leaves — nothing adopts or ranks `ci-soak-finding` items — is recorded as a tracked follow-up work-item rather than asserted as a hollow MUST.

### Motivation

The ratified clause (v045) requires the nightly to derive a stable finding signature, persist it on the filed work-item, and file only when no NON-CLOSED chore already carries it. That behavior is correct and is PRESERVED here.

What is no longer accurate is the clause's closing sentence, "This requires CI to hold credentialed access to the work-items backend per the Beads/Fabro Family Secret Convention below." The sanctioned path for off-host CI to write beads is now settled in `dolt-server` and is deliberately narrower:

- The Dolt database port MUST remain bound to loopback and MUST NOT be exposed for CI writes (`dolt-server` constraints.md, "Localhost-only" and "Beads CI write surface"). An earlier console proposal to expose the SQL port over the tailnet was rejected for contradicting that ratified posture.
- CI files by SSH to the host, through a forced command pinned in the `ci-writer` account's `authorized_keys`, whose request shape is exactly one line: `create <fingerprint> <base64url-title> [<base64url-body>]`. The tenant and issue prefix are baked into the `command=` by the operator and are never chosen by the caller.
- `dolt-server` requires that CI "MUST NOT carry the database password" and "MUST authenticate to the ingress with an SSH key alone"; the host runs its own pinned `bd` under a sealed `ci-writer` credential profile holding only the beads write set.
- Deriving the finding fingerprint is explicitly the consuming caller's responsibility — i.e. ours, specified here — and the ingress constrains it to `^[a-z0-9]([a-z0-9-]{0,62}[a-z0-9])?$` (a DNS-label-like slug of at most 64 characters).

The surface's dedup matches this clause: it lists OPEN chores carrying the finding's metadata field and no-ops when one exists, and it deliberately assigns NO fixed work-item id so that re-filing after a close does not collide with the closed chore. This was verified empirically on 2026-09-06 against the live ingress: filing a fingerprint created one chore; re-sending it while that chore was open filed nothing; closing the chore and re-sending the SAME fingerprint filed a NEW chore. Re-file-after-close therefore works end to end and this clause's semantics need no change.

(The divergence that prompted this — `dolt-server`'s constraints.md previously describing the dedup as a deterministic `bd --id` that suppresses re-filing permanently — was reported to that repo as `dolt-server-2u6jll` and has since been CORRECTED there in its v021, which now normatively requires the `ci_fp` metadata dedup key, OPEN-only suppression, mandatory re-file after close, and a server-assigned id. That repo's spec and implementation now agree, and this proposal matches both.)

A second correction, surfaced by the ratification review of this proposal's first draft: amending only the idempotency paragraph left THREE surviving statements elsewhere in this file contradicting it — the primary filing sentence still routing through the orchestrator's capture surface, the Family Secret Convention still requiring CI to hold `BEADS_DOLT_PASSWORD` for work-items access and naming nightly chore-opening as its example, and Contributor Scenario E restating that as a coverage-linked scenario. A partial amendment would have ratified two mutually exclusive MUSTs. All three are amended here.

The same review established that the shipped ingress passes only title, `--metadata`, `--external-ref`, `--label ci-soak-finding`, `--type task` (plus an optional `--description`) — it carries NO priority or rank field. The ratified "top of the rank order" obligation is therefore unsatisfiable at the filing step.

A third review round established that RELOCATING that obligation to the `pending-approval -> ready` transition — the draft's first repair — does not fix it either, because an ingress-filed item cannot REACH `pending-approval`:

- The ingress performs exactly one `bd create`, and `bd create` (v1.2.2) has no `--status` flag. Verified directly: `bd create --dry-run --json` against this tenant returns `"status": "open"`.
- The orchestrator's five lifecycle states are CUSTOM beads statuses (`contracts.md`, "Work-item beads-issue mapping"). `bd create` forces an `open`/`deferred` initial status, so EVERY initial-state write is a two-step path — "even a plain `file`, since `backlog` is itself a custom status."
- `dolt-server`'s constraints.md forecloses step two for CI by design: the SSH surface MUST remain single-verb (`create`), with no listing verb.

So the filed item lands at beads `open` — a status the orchestrator declares superseded and maps to NONE of its lifecycle states — and unranked. `pending-approval -> ready` is not the next transition; it is two undefined hops away, and no clause in either specification obliges anyone to make either hop. Corroborated live: the two enrollment smoke chores filed through the ingress (`livespec-console-beads-fabro-sjym`, `-wdm4`) carry `metadata = {"ci_fp": ...}` and nothing else — no rank, no priority beyond `bd`'s substrate default.

This proposal therefore does NOT relocate the obligation. It states the truth instead: the ingress files at beads `open`, outside the orchestrator's lifecycle states and unranked, and the specification asserts no transition or ranking that no actor performs. Adoption-and-ranking of `ci-soak-finding` items is a real product gap — nightly findings would be filed and never picked up — and it is recorded as a tracked follow-up work-item rather than papered over with a hollow MUST. The alternative (specify an adopter first, then re-assert a ranking obligation) needs new orchestrator or intake work and does not ship with this amendment.

A fourth review round found a second substrate-false claim, introduced by this proposal's own earlier draft while repairing the credential posture. That draft asserted that "any HOST-side process that needs work-items access MUST obtain `BEADS_DOLT_PASSWORD` through the same convention" and that "the host-side `bd` the ingress runs is what obtains the secret through this convention" — restated a third time as a mermaid EDGE (`OP --> Bare --> HostBd --> Beads`) in Contributor Scenario E, the fenced-block blind spot again. It is false. The ingress host is `dolt-server`, and its `ci-writer` path runs `bd` through `with-dolt-server-env.sh`, a wrapper ratified to NEVER nest the family wrapper and to actively CLEAR ambient fleet credentials, backed by systemd-creds rather than 1Password. `dolt-server`'s constraints.md requires that "the wrapper profile `ci-writer` MUST load ONLY the sealed ci-writer database password — a systemd-creds ciphertext credential `dolt-server-ci-writer-password` — and MUST NOT load any family, dispatch, or viewer credential". So the draft did not merely misdescribe the substrate; it put this specification in direct contradiction with the owning repo's ratified MUST NOT, and it broadened a clause that had bound only CI into one reaching host processes this repository does not own. This proposal therefore scopes the convention to processes IN THIS REPOSITORY and explicitly declines to assert how the ingress host credentials its own `bd`.

Finally, the ingress is reachable only from the tailnet. A GitHub-hosted runner has no tailnet identity, so a nightly scheduled onto one could not file at all. That must be an explicit, loud failure rather than a silent no-op that leaves the soak looking healthy while tracking nothing.

### Proposed Changes

In non-functional-requirements.md, AMEND the nightly chore-filing clause (the paragraph beginning "Nightly chore filing is **idempotent**: ..."):

- KEEP UNCHANGED the dedup semantics: derive a stable finding identity from the inputs already ratified (for a fuzz crash, a hash of the reproducing input or the crash backtrace; for a surviving mutant, its `(source file, line, mutation-operator)` identity); file only when no NON-CLOSED chore already carries that identity; re-file once a previous chore for the finding has been closed. Keep the recorded trade-off that a pre-existing open chore MAY be stale.
- QUALIFY the dedup obligation as OBSERVATIONAL rather than atomic, and bind it to the ingress as the actor that performs it. Master's unqualified "It MUST NOT file a chore when an open (non-closed) chore already carries that signature" was already loose; pinning the suppression to the ingress (which this amendment does) would turn that looseness into a direct contradiction with `dolt-server`'s ratified constraints.md, which states that "two concurrent runs for the same finding MAY each observe no open chore and both file; this benign list-then-create race is accepted... and MUST NOT be worked around by widening the surface." State the accepted race explicitly, and weaken the closing obligation from "tracked at least once" alone to "at least once, not exactly once", so the spec does not promise an at-most-once guarantee the single-verb surface cannot provide.
- ADD that the finding identity MUST be rendered as a FINGERPRINT matching `^[a-z0-9]([a-z0-9-]{0,62}[a-z0-9])?$` (a DNS-label-like slug of at most 64 characters), which is the dedup key.
- REPLACE the filing mechanism: the nightly MUST file through the `dolt-server` on-tailnet SSH write ingress using its single `create <fingerprint> <base64url-title> [<base64url-body>]` request, rather than reaching the work-items backend itself. The ingress performs the host-side filing, records the fingerprint on the work-item so the existence check stays cheap, and assigns no fixed work-item id so a re-file after close cannot collide. (The ingress in fact carries the fingerprint in BOTH a metadata field and an `--external-ref`; the spec records the obligation, not that two-field mechanism, which is `dolt-server`'s to change.)
- REPLACE the sentence "This requires CI to hold credentialed access to the work-items backend per the Beads/Fabro Family Secret Convention below." with: CI MUST NOT hold the work-items database credential. CI authenticates to the host write ingress with an SSH key ALONE; the host runs its own pinned `bd` under a sealed `ci-writer` credential profile that loads no family credential, and the database port remains bound to loopback. The Family Secret Convention continues to govern this repository's own processes -- not CI-held credentials, and not the ingress host's, which `dolt-server` governs under its own sealed profile.
- ADD a fail-closed requirement: the nightly soak MUST run on the self-hosted, on-tailnet runner pool. Because the write ingress is reachable only from the tailnet, a nightly scheduled onto a runner without tailnet identity (for example a GitHub-hosted runner) MUST fail loudly rather than complete while filing nothing.

In non-functional-requirements.md, AMEND the PRIMARY filing sentence of the nightly clause (the one beginning "A nightly finding ... MUST NOT fail the canonical branch; it MUST instead file a chore work-item ..."), which the first draft wrongly left untouched: filing routes through the tailnet beads write ingress, NOT the orchestrator's capture surface. State truthfully that the ingress files with a single `bd create`, a request surface admitting no lifecycle status, rank, or priority, so the item lands at the beads default `open` status, OUTSIDE the orchestrator's lifecycle states, and unranked. REMOVE the "top of the rank order" obligation rather than relocating it, and assert NO transition out of `open`, because no actor performs one. Narrow the filing guarantee to what is real and checkable: the finding is durably recorded in the tenant, labelled `ci-soak-finding`, carrying its fingerprint, and recoverable by label. Keep unchanged the MUST-NOT-fail-the-canonical-branch requirement and the never-filed-into-`ready` invariant. State explicitly that adopting such an item into the orchestrator's lifecycle, and ranking it once adopted, is a known gap this specification does not close and is tracked as open work in the ledger.

In non-functional-requirements.md, AMEND the embedded contributor scenario "A nightly finding opens a chore instead of failing master": its "through the orchestrator's capture surface" step is superseded — the chore is filed through the tailnet beads write ingress, carrying the fingerprint and the `ci-soak-finding` label, landing unranked at the beads default `open` status outside the orchestrator lifecycle states, with no transition out of it asserted. Keep unchanged: the canonical branch does not fail, and the chore is filed in the `livespec-console-beads-fabro` tenant.

In non-functional-requirements.md, AMEND the Beads/Fabro Family Secret Convention sentence "CI MUST obtain `BEADS_DOLT_PASSWORD` through the same convention when it needs work-items access (e.g. the nightly chore-opening above)." It directly contradicts the new MUST NOT and names this very use case. Replace it so the convention binds every process IN THIS REPOSITORY that needs work-items access and states that CI MUST NOT hold the secret. Do NOT assert how the ingress host credentials its own `bd`: that host is `dolt-server`, and its ratified constraints.md requires the `ci-writer` wrapper profile to load ONLY a systemd-creds-sealed `dolt-server-ci-writer-password` and "MUST NOT load any family, dispatch, or viewer credential", with `with-dolt-server-env.sh` ratified never to nest the family wrapper and to actively clear ambient fleet credentials. Claiming the ingress host obtains the family secret "through the same convention" would be substrate-false AND would put this spec in direct contradiction with the owning repo's ratified MUST NOT. State instead that the ingress host's credentialing is governed by `dolt-server`'s own sealed credential profile and is out of this convention's scope.

In non-functional-requirements.md, AMEND Contributor Scenario E's "CI obtains the secret through the same convention" scenario, which restates the same contradiction as a coverage-linked scenario: CI authenticates to the tailnet write ingress with an SSH key alone and never obtains `BEADS_DOLT_PASSWORD`, and how the ingress host credentials its own `bd` is left to `dolt-server`'s sealed credential profile rather than asserted here. Scenario E's mermaid diagram carries the same claim as an EDGE (`OP --> Bare --> HostBd --> Beads`) and MUST be amended with it: the family wrapper's bare secret flows to THIS repository's own processes, while CI reaches the tenant through the ingress on an SSH key, and no edge runs from the family secret to the ingress host. The `Contributor Scenario E -- Beads/Fabro family secret convention` heading and its pending `test: TODO` registration are unchanged; its CLAUSE list is not — the rewritten convention sentence retires one `gap_id` and mints two, so that entry is co-edited alongside Scenario C's.

`tests/heading-coverage.json` MUST be co-edited atomically in the same change. `console-spec-check` links clauses by `gap_id` — a digest over `(spec file, heading path, clause LINE)` — so every amended or added normative line yields a NEW `gap_id` and orphans its previous registry entry. Amending the clause without the co-edit takes this repo from 0 unlinked clauses to 11 and fails the check. The co-edit registers each new clause line against its owning live scenario: the nightly-clause lines under `Contributor Scenario C -- Quality gate enforces the inner and merge loops`, and the Family-Secret-Convention lines under `Contributor Scenario E -- Beads/Fabro family secret convention`.

The nightly entry's linked TEST (`crates/console-nightly-soak/src/lib.rs::tests::fuzz_finding_with_no_open_chore_files_exactly_one_chore`) is deliberately left pointing where it is: it still exercises the dedup behavior this amendment leaves unchanged. Re-pointing the test belongs with the LATER implementation rework that replaces the filer's transport; naming the reworked tests now would register tests that do not yet exist. Any gap_id left dangling by a reflowed line MUST also be removed from the registry rather than left as a false coverage claim.

`crates/console-spec-check/src/tests.rs` MUST be co-edited in the same change too. That test pins the normative-clause ground truth per spec file and in total, so a SPEC-ONLY edit breaks Rust CI — the coupling recorded in `.ai/spec-check-and-ci-discipline.md`. This amendment nets +8 clauses in `non-functional-requirements.md` (59 -> 67), moving the total from 245 to 253. The net figure hides the real shape, which the co-edited comment MUST record accurately: 11 clause LINES are added and 3 removed (verified against the registry: under Contributor Scenario C, 8 `gap_id`s added and 2 orphaned; under Contributor Scenario E, 3 added and 1 orphaned; all 3 orphans deleted). Because rules are extracted per LINE, a reworded MUST retires one gap_id and mints another rather than counting as new, and a MUST that wraps across two lines counts twice — so a roster of "eight new rules" would be arithmetically right and factually wrong.

On the deliberate REMOVAL rather than relocation of "top of the rank order": an obligation must name an actor AND bind to a trigger that actually occurs. "Rank it when it is triaged" is hollow because nothing compels triage. "Rank it at the `pending-approval -> ready` transition" is worse than hollow, because the item never reaches `pending-approval` at all — it sits at beads `open`, two undefined hops away, and asserting the obligation there would put a false requirement into the ratified specification. Removing it is a genuine reduction in force and is recorded as such here, not disguised as a clarification. The force is not silently dropped: the gap it leaves — nothing adopts or ranks `ci-soak-finding` items, so nightly findings can be filed and never picked up — is filed as a tracked follow-up work-item under this repo's test-adequacy-gates plan epic, and closing that gap is the prerequisite for re-asserting any ranking obligation in a later amendment.

Keep unchanged: the MUST-NOT-fail-the-canonical-branch requirement and the never-filed-into-`ready` invariant. NOT unchanged, and deliberately so: top-of-rank-order placement is REMOVED, not moved; the intake Definition-of-Ready and `admission_policy` routing is no longer asserted for these items at all, because nothing places them into the lifecycle where that routing applies.
